# Architecture Debt Register

Every accepted exception to the rules in [ARCHITECTURE.md](../../ARCHITECTURE.md) is recorded here with an owner and a review date. An exception that is not listed here is not accepted — it is a defect.

## How an entry gets here

1. ADR written (edge, reason, alternatives tried, cost of not having it)
2. Architecture review approved
3. Narrow exception added to `.importlinter` — specific module to specific module, never a wildcard
4. Row added below

| D-006 | Three modules added to the `unscoped` manager allowlist: `platform/audit/services.py`, `commercial/subscriptions/selectors.py`, `commercial/subscriptions/system.py` | Tenant-scoping bypass | Clock-driven commercial transitions have no actor and so no `TenantContext`, and they must work for **suspended** organizations whose writes R-10 blocks under any context. | D-008 | `ecosystem.AuthorizationCode` carries `organization_id` without being a `TenantScopedModel` | W360.E001 exemption | The token endpoint has **no tenant context and cannot have one**: there is no session, no membership and no organization until the code is found, and the code is what establishes them - a tenant-scoped manager would require the answer in order to ask the question. Encoding the organization in the code was rejected: it would leak the tenant identifier to whoever holds the code, before anything about it is validated. Protected instead by being reachable only through the SHA-256 of a 256-bit random secret, additionally bound to one client, one redirect URI and one PKCE challenge, and valid for sixty seconds. Same class as `identity.User` and the same precedent as `events.OutboxEvent`. See [ADR-020](adrs/ADR-020-signing-keys-and-the-control-plane-code.md). | Architecture | 2026-09-22 | 2027-03-22 |
| D-009 | The `authorize` and `client_auth_failure` rate-limit buckets are keyed partly on `REMOTE_ADDR`, which is the load balancer's address in any proxied deployment | Operational exception | `X-Forwarded-For` is client-supplied and trusting it without knowing the proxy depth lets any caller spoof an address and evade the limit entirely - a strictly worse failure than the one accepted here. The effect of the collapse is bounded and **never crosses products**: a saturated `authorize` bucket for one product does not touch another, and a client that authenticates successfully never touches `client_auth_failure`. Within one product it is reachable anonymously by anyone holding a client id and a registered redirect URI, both public by construction, so it is a sign-in availability risk for that product's customers. The fix is topology-dependent and belongs with the deployment - either a proxy that sets `REMOTE_ADDR`, or a configured trusted-proxy depth - and is documented as a deployment requirement in [docs/phase-3/14 section 11](../phase-3/14-failure-mode-review.md). Carried as R-8. | Architecture | 2026-09-22 | 2026-12-22 |

## Rules

- Suppressions in code (`# noqa: arch`) require a ticket reference and **fail CI after 90 days**.
- An entry past its review date fails the monthly architecture review until re-justified or removed.
- Adding an entry is deliberately more work than doing it correctly. That asymmetry is the point.
