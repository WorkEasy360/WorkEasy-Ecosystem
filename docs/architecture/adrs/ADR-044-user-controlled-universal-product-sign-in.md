# ADR-044: User-controlled universal product sign-in

- Status: accepted (2026-10-12)
- Context: the universal user-controlled SSO brief (record: `docs/universal-sso/status.md`, design: `docs/universal-sso/design.md`)
- Builds on: ADR-018 (OIDC for products), ADR-021 (launcher), ADR-033 (session registry), ADR-038 (four products and per-product trials), ADR-043 (multi-portal hosts and central sign-in)

## Decision

1. **One identity provider, products are OIDC clients.** Signing in once to Workeasy360 opens every entitled product that uses Workeasy360 sign-in, through the existing authorization code + PKCE flow. No password, password hash or product password ever crosses the boundary; no token is put in a query string; the products hold their own sessions.
2. **The product declares, the person chooses.** Manifest `2026-10-12` adds `sign_in_mode` (`sso_only` by default, `sso_optional`, `local_only`) and `login_url` (the product's own approved sign-in page, required for `sso_optional`). The person chooses a default for every product (Automatic / Ask each time / Prefer the product's own sign-in; nothing stored meant Ask, and means Automatic since item 14) and optional per-product overrides (`inherit` deletes the override). One table, `ecosystem_user_sign_in_preference`, keyed by user and product code (`''` = the default); no organization column and no RLS, because a preference belongs to the person, not to an organization.
3. **One resolution function.** `contracts.values.sign_in.resolve` combines them: a product that is not SSO-ready (not active, `local_only`, or no usable credential) is always "Separate product sign-in required"; a wish for the product's own sign-in where the product has none becomes Ask (the person's wish not to be signed in automatically still holds). Nothing names a product, so a product registered tomorrow follows the person's default with no code change.
4. **The preference is enforced at the identity provider.** The authorization endpoint applies it after every membership, organization, access-policy, entitlement and seat check, so a preference can never grant access and a refusal is never hidden behind a question. Automatic issues the code silently; Ask (and a product-login preference reached anyway) parks the request and shows the access chooser on the auth host: Continue with Workeasy360, Use the product's sign-in (only when offered), Remember my choice, Use another Workeasy360 account, Cancel (`access_denied`). A parked request is bound to the person signed in; a resume link cannot skip the chooser. The launcher routes a product-login preference straight to the product's `login_url`, with no organization hint.
5. **OIDC completed where products need it.** `prompt` (`none`, `login`, `consent`, `select_account`), `auth_time` in the ID token, and RP-initiated logout (`end_session_endpoint`) with a confirmation page, because a GET cannot sign anyone out. New error codes: `access_denied`, `unauthorized_client` (a `local_only` product) and `interaction_required`.
6. **Products keep their side of the contract.** Easy CRM and EasyBook re-check entitlement through the existing entitlement API on Workeasy360's cadence, and refuse an organization whose access has ended (`workeasy360_access_ended`) or writes while it is read-only. A platform outage is never a denial; a refusal of the product's own client is (`workeasy360_access_unverified`), and a known denial never lapses into access. Easy CRM's "Confirm it's you" requires a linked account, a fresh `auth_time` and the same `sub`, and an account linked to Workeasy360 gets no local password. Without the re-check, a product session opened during a trial outlived the trial: EasyBook's rotating refresh token made that indefinite.
7. **Not SSO-ready means refused, never offered.** An active integration without a usable credential is refused at the authorization endpoint (`unauthorized_client`) whatever the preference: no chooser leads to a code the product could never redeem.
8. **New products join through the console.** The Super Admin Authentication section registers an integration, sets the mode and URIs, adds a public key or generates a client secret (shown once), and activates. Its state reads Enabled / Disabled / Integration required from server facts. No code path names a product.
9. **Sign-in once across hosts.** A Workeasy360 session that slides its idle window now slides the other live sessions of the same sign-in (ADR-043), so the `auth.` session does not lapse while the person works on `app.`.

## Consequences

- (Superseded by item 14.) Default behaviour changed for products that were always signed in silently: with no preference stored, the person was asked once per launch until they chose Automatic or remembered a choice. That was this brief's recommended default.
- A preference change applies on the next launch; nothing already open is signed out.
- Signing out of Workeasy360 does not end product sessions (no product implements front- or back-channel logout). After access ends, a product keeps serving for at most one re-check window (15 minutes), not for the life of its session.
- (Superseded by the addendum below.) Easy Project and Easy Help Desk had no client code in reach and were registered `local_only`.
- Rejected: storing preferences per membership (they belong to the person); applying preferences only in the portal (products that start sign-in themselves would bypass them); trusting a hostname or a preference as authorization; a shared parent-domain cookie; front- or back-channel logout without a product contract.

## Addendum (2026-10-12): all four products, people as well as organizations, background work

Brief "UNIVERSAL SSO FINAL COMPLETION". `docs/universal-sso/completion-design.md` is the design; `capacity.md` the sizing.

10. **Easy Project and Easy Help Desk are OIDC clients too**, with the same contract (completion-design §3), and are registered `sso_only`. Their code was found in the `WorkEasy360` GitHub account (`Project-Module`, `helpdesk-workeasy`). Easy Project's trusted `X-User-Id`/`X-Org-Id` headers (the Phase 12 P0) are removed, not kept as a fallback.
11. **The entitlement API can answer for a person.** An optional `subject` (the ID token's `sub`) adds sign-in's personal checks (account usable, membership active, seat for a per-seat product) through the same functions sign-in uses. It answers `membership_inactive` or `no_seat`, and one answer covers removed, never-a-member and unknown. Products send it for a signed-in person's requests. Before this, a removed member or an unseated person kept working until their product session ended; now it is at most one window (15 minutes), the same as a lapsed trial. Additive: without `subject` the answer is unchanged.
12. **Background work re-checks entitlement before a customer business effect.** Jobs are classed: A (automations, outbound mail and messages, webhooks, recurring documents, syncs, AI, SLA escalations) needs `allow` and `write_allowed`; B (cleanup) and C (retention and maintenance) run regardless. A denied class-A job is skipped and logged, not retried in a loop, and resumes after renewal. An outage is not a denial.
13. **The verify limit is sized from a model.** `W360_RL_VERIFY` goes from 600/min to 1,200/min per client, and a new `W360_RL_VERIFY_ORG` allows 6/min per (client, organization, person). Rejected: an "enormous" limit, which would remove the API's protection against one product; a longer `revalidate_after`, which would lengthen the window for every cause of lost access.

## Addendum (2026-10-12): one login for all products

Brief "WORKEASY360 - ONE USER LOGIN FOR ALL PRODUCTS". Design: `docs/universal-sso/one-login.md`.

14. **The default preference is Automatic.** This brief recommends "Automatically use Workeasy360" as the seamless experience: click Open, or type a product's address, and the product opens. `DEFAULT_PREFERENCE` is `auto_sso`. People who stored a choice keep it. All three choices remain, and item 4 is unchanged: the preference is applied after every access check, so the default grants nothing (`test_one_login_guards.py`). Reverting is a one-line change.
15. **A product opened directly starts the sign-in itself.** An SSO-only product that receives a page navigation with no session of its own goes straight to its own start endpoint (integration guide §6b). It never does so on its sign-in page, after the person signed out of it (a marker that lasts until the next sign-in), or within 60 seconds of a previous automatic start (loop guard). API calls are never redirected. Workeasy360 needs no change for this: its authorization endpoint already reuses its session or shows the central sign-in. Rejected: a silent `prompt=none` probe on every visit, which would cost one extra round trip each time and still need the same fallbacks; auto-starting on the product's sign-in page, which would make "Sign out of <product>" meaningless while Workeasy360 is signed in.
16. **A request that names no organization means the person's only one.** A product opened by typing its address has no organization to name. Until now every such request went to the organization chooser, even for a person with one organization: a question with one answer, and a step in the brief's "type the address, open signed in" journey. Now `authorization.organization_for` uses the named organization, else the person's only organization (`organizations.resolver.sole_organization_id`, read from the chooser's own projection). The implied organization is then resolved, policy-checked, entitlement- and seat-checked and bound into the code exactly like a named one. Someone in several organizations is still asked, never guessed for. The implied organization is never stored on the parked request: the access chooser shows it to its person, and a resume computes it for whoever resumes. Storing it would let "Use another Workeasy360 account" hand the first person's organization to the next one (the independent review's P2). Also from that review: a request parked for sign-in or for the organization chooser, and resumed by a session that was already signed in before it was parked, now applies the person's preference exactly as `authorize` does. Before, a resume link opened in a signed-in browser, or an organization picked by someone set to "Ask me each time", completed with no question. A person who signs in for the request is not asked again. The cost is a narrow double question: someone in several organizations, set to Ask, opening a product that named none, picks the organization, answers the chooser, and is then asked for the organization once more. This supersedes `docs/phase-3/03-sso-architecture.md` §3's "no only-organization fallback". That rule's concern was that the behaviour silently changes on joining a second organization; now it changes into a visible question, which is the right change. Rejected: a product-side "last organization" cookie, which does nothing for a first visit; and asking anyway, which keeps the extra step for nearly everyone.
