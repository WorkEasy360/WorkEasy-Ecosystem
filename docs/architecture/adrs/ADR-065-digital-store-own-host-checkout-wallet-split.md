# ADR-065: The Digital Store on its own host - store.workeasy360.com, one-product checkout with a Platform Wallet split, Recharge, and My Account's pass to User Admin

Date: 2026-11-12. Status: accepted; built on `feat/partner-admin-panel`, not committed or deployed yet. Amends ADR-043 (the portal table: a fifth, optional web portal), ADR-052 (the public cart: no longer offered in the Store), ADR-053 (where `/store/...` and the Store referral link live), ADR-059 (the Store signs its customers in on its own host), ADR-060 (a customer may pay from its own Platform Wallet, in full or in part) and ADR-064 (the User Admin's "Store" is now its own site).

## Context

The owner's brief "WorkEasy360 – Digital Store: complete development, UI/UX, domain and system integration update" (12 November 2026), with two reference images (a checkout and a marketplace home), asked for the existing Store to become a production marketplace at **https://store.workeasy360.com/**, with four menus (Products, Recharge, Partners, Help), a one-product checkout that can pay from the Platform Wallet and the gateway together, three separate recharges, My Account linking into User Admin, partner programmes on the shared application and KYC, policies, and the domain configured end to end. It named `08_Credits_Wallets_System.txt` and `07_Product_Web_Mobile_Flow.txt` as authoritative; neither is on this machine or in git (as on 2026-11-09, ADR-060), so this follows the brief and leaves what they would decide open.

The audit found the Store at `app.workeasy360.com/store` (ADR-052/053) with a public multi-product cart, no Platform Wallet payment for customers (staff only, full amounts only, no hold), no reservation anywhere in the ledger, no public usage rates or credit packs, payment returns always to the console, no legal pages, no reserved partner codes (a page under `/store/` hides a partner of the same code), and a `robots.txt` that disallows everything.

## Decision

1. **A fifth web portal, `store`, optional.** `W360_STORE_ORIGIN` (backend `contracts.values.portals.STORE`, frontend `lib/portals.ts`). Unset - today's production - nothing changes and the Store stays on the customer portal. Set, the Store's host owns every `/store/...` page; the same paths, so every existing deep link (`/store/product/<slug>`) opens there, and `app.../store/...` redirects to the same address on the Store's host (302, query kept). The Store host's `/` *serves* the marketplace (a rewrite, not a redirect). Production's assertions accept the five required origins plus `store` when set, and require it in `W360_ALLOWED_HOSTS` and `W360_CSRF_TRUSTED_ORIGINS`.
2. **Its own session, the same accounts.** The Store host serves `/login`, `/signup`, `/verify-email`, `/forgot-password`, `/reset-password` and `/r/<code>` itself (the sign-in endpoint is allowed on every web portal), so the session, the referral cookie the visitor followed and the purchase they chose stay on one host; an emailed link (verification, reset, "you already have an account") opens on the host it was asked from (`identity.portals.request_portal` / `account_url` for `ACCOUNT_PORTALS`). A sign-up started in the checkout returns to that checkout after verification (`features/store/storeReturn.ts`, a `/store` path only).
3. **The Store host's API is a narrowing of the customer portal's.** `PortalSurfaceMiddleware` serves the Store host only the organization endpoints its checkout and Recharge use - `access`, `orders` (quote, place, read, cancel), `billing-account`, one invoice and its `pay`, one payment, `wallets` (overview, top-up, credit packs), `trials`, `notifications` (`STORE_UNDER_ORGS`). Members, security, integrations, settings and the rest stay the customer portal's alone. The cross-origin write refusal applies to the Store host like every web portal.
4. **My Account: a single-use pass to User Admin.** `POST auth/account-pass` (Store host only, signed in) issues an `identity.handoff` code marked `via=store_pass` for a `safe_next` path of the customer portal; the Store page posts it in a form body to `POST auth/account-pass/enter` (customer portal only; CSRF-exempt and listed in `TICKET_VIEWS`), which requires `Origin` = the Store origin (no login CSRF), spends the code once, re-checks the account and the Store sign-in are live, and opens User Admin's own session for the same sign-in (303 to the page). A pass is never a hand-off code and the other way round. The CSP's `form-action` names the customer portal on the Store host only.
5. **One product, one plan, one organization per order.** The Store checkout (`features/store/Checkout.tsx`) quotes and places a single plan through the existing order endpoints (identifiers only; the server prices again, adds GST and the coupon, refuses what is not for sale). The public cart is gone from the Store (the console's own cart is untouched).
6. **The Platform Wallet pays all or part of an eligible invoice.** `POST billing/invoices/<id>/pay` takes an optional `wallet_amount_minor` (`payments.wallet_orders.member_pay_invoice`, `platform.billing.manage`): `0` is the provider alone; the whole amount due is the wallet alone (`member_pay_from_wallet`, settled at once, any provider payment in flight withdrawn - money that still lands there is refunded as for any closed invoice); anything between is a **split**: the wallet's part is held (`wallets.WalletHold`, `ledger.hold`) in the same transaction that starts the provider payment for the rest, the provider's verified success **captures** it inside the settlement's transaction as a second, wallet, payment attempt (so the invoice is paid by exactly the two amounts and a refund names each), and a failed, expired or cancelled payment, a cancelled or expired order and a voided invoice **release** it (each path, explicitly; `expires_at` is a backstop only). While a hold is live no other debit may spend that money (`ledger.post`). A late success after a release takes the wallet's part again when the wallet still can, otherwise the invoice keeps owing it. Never for a wallet's own order (top-up, credit pack). Holds and their outcomes are audited.
7. **The payment returns to the Store.** `PaymentAttempt.return_portal` records `store` for a payment started on the Store host; the provider's success and cancel addresses (and the development provider's page) are then the Store's `/store/checkout/complete`, which asks the server what happened - the return itself proves nothing.
8. **Recharge, three separate ways.** The Platform and Consumption wallets take a free amount and AI Credits a pack - each an order paid online only (`wallet_amount_minor` 0), credited by fulfilment once. `GET public/store/recharge` publishes exactly what an Admin entered: the live usage rates (money meters in the page's currency, AI tokens in credits) and the active credit packs, plus whether online payment is open (`GET public/store/payment-option` names the provider's kind only).
9. **Product data the Store shows.** The public plan carries `recommended`, `renewal_rule` and `included_usage`; the product page carries `setup_requirements` (a new merchandising list, `catalog.0013`) and `access` (the web app, and only the https app-store links the Super Admin entered). A product's own site may send a buyer to `/store/buy?product=&plan=&interval=&ref=&return_to=` (codes only); the return address is shown only after `GET public/store/return-check` approves it against the product's registered launch and return destinations.
10. **Policies are the Super Admin's.** Help content gains kind `policy` with eight fixed keys (Terms, Privacy, Refund & Cancellation, Subscription, Platform Wallet, AI Credits, Consumption Wallet, Partner Terms); the Store shows a policy only once published, and says plainly when it is not. FAQs describe how the system works and point to what the Super Admin sets; no refund window, rate or promise of the Store's own.
11. **Partners on the shared application.** `GET public/store/partner-programme` returns whether applications are open, the Affiliate and Reseller programmes in the platform's own words, the active KYC requirements (label, help text, required) and the stages. White Label is not offered publicly. Apply and Application Status are on the Partner portal; partner codes that are Store pages (`checkout`, `help`, `partners`, `policies`, `products`...) are reserved (`partners.domain.RESERVED_CODES`; Add Partner picks `help-2`).
12. **Search.** Each Store page sets its canonical address on the Store origin (`lib/storeMeta.ts`; the marketplace is the host's root), checkout and confirmation are `noindex`; `robots.txt` is per host (the Store host allows `/store` and names its sitemap, every other host still says `Disallow: /`); `sitemap.xml` is built by the API from configuration and the public catalog.
13. **The edge.** The Caddyfile's Store site exists only when `W360_STORE_EDGE=on` (a snippet import), so the certificate is requested only once DNS exists; it routes `/api/*` to Django, `/sitemap.xml` to the API's sitemap and the rest to the web app. `deploy/single-host/make_env.py enable-store|disable-store` switches the four values (origin, edge switch, hosts, CSRF origins) together.

## Consequences

- Production is unchanged by deploying this until the owner adds the DNS record and `enable-store` is run; the new Store UI then serves from `app.workeasy360.com/store` meanwhile.
- A buyer who opens User Admin from the Store keeps one sign-in: signing out of the Store ends the User Admin session the pass opened (the hand-off's sign-in id).
- A split payment leaves two succeeded attempts on one invoice; a refund is per attempt (the wallet's goes straight back to the wallet).
- Open, because the two named specifications are missing: GST on wallet top-ups and credit packs (none is charged), credit expiry, minimum top-ups, refunds to wallet or source, renewal from the wallet, and any rule for purchases made inside the mobile apps (the Store sells on the web only; app links are links).
- Live payments still need the owner's Razorpay credentials (unchanged); the checkout says when online payment is not available.
