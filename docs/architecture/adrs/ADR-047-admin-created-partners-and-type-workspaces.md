# ADR-047: Admin-created partners with a login, and the Reseller, White-label and Affiliate workspaces

Status: accepted, 2026-10-22. Builds on ADR-041 (Partner Control Center), ADR-042 (setup, profile and contacts), ADR-043 (portal hosts), ADR-045 (business panel) and ADR-046 (final menu). Changes none of them; adds to each.

## Context

Super Admin could create a partner, but not the partner's sign-in: the administrator was invited by email and chose their own password. The owner asked for the opposite for this flow: Super Admin types the partner administrator's email **and password** on the Add Partner screen, tells the person privately, and the person signs in with exactly those at the partner portal - landing in a Reseller, White-label or Affiliate workspace - with **no** temporary password, **no** invitation, and without any of the platform's identity, entitlement, commission or tenant rules changing.

## Decisions

1. **There is still exactly one kind of partner.** `PartnerAccount` plus its `PartnerCapabilityGrant`s. "Reseller", "White-label" and "Affiliate" are *labels derived from grants* (ADR-041) and, at creation, **presets**: a list of registry keys (`capabilities.EXPERIENCE_BUNDLES`) applied through the ordinary `grant_capability` command. Choosing a card stores no type; no code reads a partner type (there is none): architecture tests pin that no partner type model or column exists and that `partners.0007` adds exactly one column and one CHECK - the presentation preference below.
2. **`default_experience` is a presentation preference.** One short, CHECK-constrained column (`partners.0007`, additive, `db_default=""`) that selects *among* workspaces the grants already open (`capabilities.resolve_landing`). It grants nothing, removes nothing and is read only to choose where the portal opens; tests fail if authorization code reads it, or if changing it changes any resolved permission.
3. **One atomic command makes the partner and the login** (`controlplane/partner_onboarding.create`). Validation of the whole form precedes the first write; then one transaction, under advisory locks on the email and the partner code, calls the existing services (`create_partner`, `profile.update_profile`, `grant_experience`, `grant_product`, `set_partner_price`, `assign_partner_commission`, `attach_user_as_member`, `set_partner_status`). A failure at any step leaves no user, member, grant, price, rule or partner. `create-review` is the same code as a dry run and never receives a password.
4. **The password is Super Admin's input and nothing else's.** The new user is made by `identity.lifecycle.create_account`, which hashes with the configured hasher (the platform's password policy applies; nothing is weakened). The password travels in two requests (`credentials-check`, `create`), both `no-store`; it is in no response, audit event, outbox event, notification, log line or exception context, nor in any `repr` of the objects that carry it, and the views and commands that read it mark their frames sensitive so Django's error reports print none. It is at most 128 characters (the form's own limit, held by the server before any validator runs on it). The create answer is ids and facts (partner id, code, status, administrator email, whether an account was made). The browser keeps it in React state only, empties the fields after the request, and uses `type=password`, `autocomplete=new-password`.
5. **An existing email is never overwritten.** The check says "This email already belongs to an existing Workeasy360 account." and offers **Link existing user as Partner Admin** (mode `link_existing`, which *refuses* a password) or **Cancel**. A disabled, locked or not-yet-set-up account cannot be linked, and neither can a **staff** account: staff and partner access are separate doors, so one identity is never made to hold both and a mistyped address that matches a colleague links nobody. A password changes only through the existing reset workflow (`send_member_password_reset`, a link to the person - never a password shown to staff).
6. **The server decides which workspaces exist.** `workspaces(held)` is a pure function of the grants (White-label subsumes Reseller, `SUBSUMED_BY`); `/partner/portal` returns `workspaces`, `default_experience` and `landing`. A switcher is drawn only for a partner that legitimately holds several. Authorization is unchanged: every request is checked again by the service it reaches, by permission, never by workspace.
7. **Workspaces are navigation compositions over one panel.** `frontend/src/features/partnerpanel/experiences.ts` is pure data (entries, the permission each needs, aliases, short addresses); the shell, `next.config.ts` and the tests read it. Routes are `/partner/reseller|white-label|affiliate/[[...slug]]` - inside the `/partner` prefix the portal host already serves, so host routing and return-URL allowlists are untouched - with `/reseller/...` etc. redirecting there. A workspace opens only for an account whose *server-derived* workspaces include it; a page outside the workspace is refused; the Affiliate workspace serves none of the customer, pricing, subscription, sub-reseller, brand or domain pages.
8. **The Affiliate workspace is its own, small set of screens** (dashboard with the referral link and copy, links, codes, campaigns, materials, leads, conversions, reports, profile). A *campaign* is the referral code's label (tracking metadata; it reaches no commission, attribution or permission). Rates are integer basis points computed by the server. No visitor is identified. Where the platform has nothing (a sign-up step, a marketing library, discount codes) the screen says so in the registry's words (`partner_portal.NOT_IMPLEMENTED`), never a zero.
9. **Changing a partner's type later is an explicit, audited transition** (`partners/experience.py`: add, retire, set primary). Adding grants the new bundle and (for a selling experience) products and removes nothing; retiring withdraws only what no remaining experience needs and **never** the money views (commission, payout); referrals, commissions, payouts and customers are never touched. "Remaining" counts every experience the grants earn, not only the workspaces: White-label contains the Reseller workspace, so a partner wearing both has one workspace but two experiences, and retiring White-label from it withdraws the brand and the domain and nothing the Reseller set needs (retiring Reseller from it withdraws only the sub-partner capability). Once no selling experience is left the partner's product grants end (stamped revoked, never deleted; its customers and their subscriptions are untouched), because products are sold, not promoted. Each change is audited with a typed reason.
10. **Prices follow the pricing view.** The products read lists a plan's prices only to a role that holds `pricing.view`, so a partner that no longer sells (or a role without it) sees plans and no price.
11. **A workspace address names no partner.** It is therefore used only when exactly one of the person's accounts holds that workspace; a person with two accounts of one kind is asked which they mean and opened into the id-scoped panel (`/partner/<id>/...`), never into the first by guess.
12. **The Partners list** shows administrator, primary experience, capabilities, products, customers, status, created and last sign-in, with row actions to view, edit, change capabilities and experience, products and pricing, commission, reset password, suspend and reactivate (all existing commands).

## Alternatives

- **A model per type** (`ResellerPartner`, `WhiteLabelPartner`, `AffiliatePartner`) or a `partner.type` column read by authorization. Rejected: it forks the account, the grants and the ledger three ways, and every future mix (Reseller + Affiliate) would need a fourth. Capabilities already say what a partner may do; the type is only a preset and a landing.
- **A temporary password, or an emailed invitation, for the administrator.** Rejected by the brief (no generated password, no password in an email) and by the owner's wish that the person signs in with what they were told. The cost is stated in section "What is deliberately not built": no forced change.
- **Overwriting the password of an existing account** when its email is typed. Rejected: Super Admin could reset a customer's password without knowing it. The existing account is linked (no password involved) or the address is changed.
- **A workspace chosen from the address bar, a cookie or local storage.** Rejected: only the server's derivation from the grants may decide which workspace exists; the address names one the server must then confirm.
- **A separate partner id in every workspace address** (`/partner/<id>/reseller/...`). Not done: it would change the host-routing and return-URL rules of ADR-043. A person with two accounts of one kind is asked which they mean instead.
- **Hashing the password before the transaction opens.** Considered (the bounded Argon2 hasher can make a request wait, and the database closes a transaction idle for 15 s). Not done: it would need a second path into the identity lifecycle for a case that cannot lose data - the command rolls back whole and can be repeated.

## What is deliberately not built

- **Affiliate "promotion scope" storage.** An affiliate's chosen products scope the *commission rule* assigned to it; there is no stored list and promoting grants no right to sell (registry key `affiliate_promotion_scope`).
- A **Signups** figure for affiliates (the platform records a visit and a conversion, nothing between), a **marketing library**, **discount or promo codes**, sub-resellers for a White-label-only partner (the White-label bundle omits the sub-partner capability), and any partner-authored pricing - all listed with their reasons in the registry.
- No MFA, password-policy or session rule changed; a Super Admin step-up is still required for the dangerous commands the flow runs.
- **No forced password change.** The brief excludes a temporary-password workflow, so the typed password is the administrator's real one (the platform's `set_temporary_password`, which forces a change at first sign-in, is the operator-demo rule and is not used). The consequence is stated plainly: whoever was told the password can sign in until its owner changes it, and the first to sign in can enrol the account's second factor. Telling the person privately, and asking them to change it, is the owner's process.

## Consequences

- One additive migration, `partners.0007_partner_default_experience`; the previous release is unaffected by it.
- Development only: Django's debug page (`DEBUG=True`) prints local variables whatever the sensitive markers say, so a crash during Add Partner on a developer's machine shows the typed password to the person who typed it. The development log format no longer prints variables (plain tracebacks, as production's JSON does).
- `partner.workeasy360.com` in production is the separate Partner Panel. This work lives in the Workeasy360 Django/Next partner portal; mapping the production partner host to it is an edge/owner step, not made here.
- Tests: `backend/tests/partner_experience/` (creation, credentials and atomicity, capability transitions, workspaces and isolation, pricing and commission, concurrency, contract shapes, architecture) and, in the frontend, `experiences.test.ts`, `workspace.test.tsx`, `affiliate-screens.test.tsx`, `add-partner.test.tsx`; the real-browser journeys are `scripts/partner_experience_browser_check/`.

## Addendum 2026-10-23: partner.workeasy360.com is this portal

The Consequence above is closed. From release `2026.10.23-95eafc4` the production partner host is served by this partner portal, through the reviewed `deploy/edge/Caddyfile`; the single-host overlay no longer replaces it. The separate Partner Panel is stopped, not deleted (`docs/partner-portal-unification/status.md`). There is one partner authentication system: the central sign-in on `auth.` (ADR-043), the Workeasy360 `User`, `PartnerMember` and capability grants. No password is copied or synchronized anywhere.

- **Landing.** `/` on `partner.` is `/partner`, which opens the workspace the server resolves (`capabilities.resolve_landing`). The workspace URLs stay under `/partner/<type>/...` (host routing and return-URL allowlists unchanged); `partner./reseller/...`, `/affiliate/...` and `/white-label/...` redirect there.
- **Primary workspace backfill** (`partners.0008`): every partner still holding the empty preference gets the workspace `resolve_landing` already gives it - white-label (which subsumes reseller), else reseller, else affiliate; none for a partner with no workspace. Explicit values are kept; capabilities are not touched.
- **Guest Login across hosts.** The guest view (ADR-048 addendum, `commercial.partners.guest`) is held per sign-in. Starting it on `admin.` now also lets the same sign-in be handed to `partner.` without a partner membership (`handoff_view` checks for a live guest view of *this* sign-in); the hand-off grants a session only, and every partner request is still authorized read-only by `guest_context`. The guest opens the partner's own landing workspace (`guest.portal_path`). "Exit Guest Session" ends the guest view and, in multi-portal mode, that partner-host session, then returns to `admin./admin/partners/<id>`.
- **A guest-only partner session is weaker and short-lived** (independent audit, P2): the hand-off re-checks the staff view grant and a verified factor; the session gets AAL 1 and no step-up time (a password or factor change there needs the second factor again) and carries the view's end (`SESSION_GUEST_UNTIL_KEY`), after which the session store deletes it whatever sliding did. Signing out ends the guest view and records it; staff partner-host sessions join the staff session trail.
- **The backfill records today's answer.** A partner back-filled as `affiliate` that is later given reseller grants keeps landing in Affiliate until an administrator sets the primary experience - before 0008 its empty preference would have followed the grants. Granting an experience in the console offers "make it the primary experience" (on by default), so the normal path still moves the landing.
- **`is_staff` reads** in `partner_views.py` moved into `control_plane_http.py` (`live_guest_view`, `end_guest_view`), the allow-listed reader; the architecture test is green again.
