# ADR-038: Registering four external products; a per-product trial independent of the subscription; a server-owned launch destination the browser fetches instead of a form 302

**Status:** Accepted
**Date:** 2026-09-29
**Deciders:** Architecture, Commercial, Security
**Depends on:** [ADR-005](ADR-005-product-entitlement-model.md), [ADR-017](ADR-017-products-are-separate-applications.md), [ADR-021](ADR-021-app-launcher-and-seat-enforcement.md) (launcher composition), [16-ecosystem-product-boundary.md](../16-ecosystem-product-boundary.md)

---

## Context

Four separately deployed products (Easy CRM, EasyBook, Easy Project, Easy Help Desk) were registered into the existing catalog and ecosystem registry. Three problems surfaced that the existing model does not answer:

1. **Product codes.** `ProductCode` is `^[a-z][a-z0-9_]{1,31}$` (no hyphen); the brief's codes (`easy-crm`, ...) are not legal codes. A code is permanent and is the leading segment of every feature key, permission and event name a product ever gets.
2. **Trialling a second product.** `Subscription.trial_ends_at` is subscription-wide, and `uq_one_open_subscription_per_org` permits only one open subscription per organization. A customer who already holds one product (subscription active) cannot start a *trial* of a second - the free-trial path raises `subscription_exists`, and a paid plan's `with_trial` flag is silently ignored once a subscription exists. The brief's mandatory multi-product dashboard state (one product active, one on trial, a third untouched) cannot be reached this way.
3. **Launching a real external product.** Every real product's `launch_url` is a different origin from Workeasy360. The launcher's `<form method="POST">` to the launch endpoint, on a cross-origin 302 answer, is refused by this application's own CSP (`form-action 'self'`) - verified in real Chrome via puppeteer-core, not assumed. The existing mechanism worked only because no external product had been launched against it before.

## Decision

**Codes are `easy_crm`, `easybook`, `easy_project`, `easy_helpdesk`.** The public *slug* (the brief's URL) is derived exactly as `slug_for_code` already does (`_` -> `-`), so `/products/easy-crm` etc. are unaffected. Registration is `manage.py register_products` (idempotent; catalog rows and a `draft` integration only - no plan, no price, no credential; those stay commercial decisions made in the console), allowlisted alongside `w360_staff_identity` for the same "no tenant context yet" reason.

**A product trial is a new durable fact (`subscriptions.ProductTrial`), not a subscription.** Tenant-scoped, RLS, unique `(organization, product_code)`. It creates no subscription, no invoice, and reaches entitlements only as a third input to `provisioning.compute_entitlements` (`EntitlementSourceKind.TRIAL`, already declared and unused until now) - never a special-cased read path. A paid line for the same product always wins over a trial in the computation, which is what makes "buy during a trial" and "already owns it" both correct with no second writer. Configuration (`catalog.ProductTrialConfig`: enabled, duration, seat limit, eligible plans) is per product and ships with **no default anywhere** - a product has no trial until staff switch one on. `payment_method_required=True` is refused outright: the platform stores no payment method (D-028), so accepting the flag would promise a control that does not exist. The sweeper (`system.settle_product_trials`) closes a trial as `converted` (a paid line now exists) or `expired` (its window passed), and access already stops at `ends_at` before either runs, exactly as a subscription's own trial does.

**Launch answers with JSON when asked, and the browser navigates itself.** `apiFetch` already sends `Accept: application/json`; the launch endpoint recognises that and returns `{redirect_url, state}` instead of a 302 on success, or a 409 with the denial state otherwise. `redirect_url` is still built entirely server-side from the registered manifest (`launcher_views._launch_target`) - the client supplies nothing about the destination, only the click. The frontend's `LaunchButton` calls it and then does `window.location.assign(redirect_url)`, a genuine top-level navigation. A plain form POST to the same endpoint still gets the 302 (nothing that depended on it breaks), but nothing in this codebase uses that path anymore.

**Manifest URLs are checked for private and metadata addresses, not only for scheme.** `_validate_url`'s existing dev-only http-loopback exemption was, by an oversight this phase's own tests caught, also exempting **https** loopback and internal hosts from the host check - `https://localhost/` would have registered. Fixed: the exemption now applies only when the scheme is `http` (the case it exists for). `https://169.254.169.254/`, `https://localhost/`, private ranges and the platform's own reserved suffixes are refused for `launch_url`, `health_url` and every redirect URI, in every environment.

**Health is probed, never trusted from the browser.** `integration/health` (a new Tier-3 app, same layer as `integration/routing`) makes the one bounded request per product, through the existing SSRF-guarded egress client (https only, every resolved address checked, no redirect followed, an 8s budget) - `platform/ecosystem` itself is architecturally forbidden any outbound HTTP, so the *result* crosses back through `ecosystem.health.record_health`, never the request. A scheduled sweep and a staff "check now" are the only callers; no customer page render ever triggers one (E-6: an external product's outage must not affect Workeasy360's own readiness, and does not - the probe has no readiness registration at all).

**Single sign-on status is read from credentials, not assumed from `active`.** An integration can be `active` with zero issued credentials - it was always representable, just never surfaced. `sso_status` (`connected` / `integration_required`) is now derived per integration (an unrevoked, unexpired credential exists) and shown on the customer's own card, the Explore listing and the Super Admin console. None of the four real products had a compatible OIDC client at registration time, so all four show `integration_required` honestly rather than a launch that would fail at the token endpoint.

**A customer's own white-label brand is resolved through its live partner link, in the canonical console - not a Host header, and not a substitute for D-035.** `brand_for_organization` mirrors `active_brand_for_host`'s exact rule (both `branding.manage` and `domain.manage` held, partner active, a brand row exists) but keys off `PartnerOrganizationLink` instead of `PartnerDomain`. It is presentation only, reached at `GET /orgs/<slug>/brand`, and the organization console shows it in place of the "Workeasy360" wordmark (never in Super Admin or the partner portal). This is deliberately a different problem from D-035: nothing here signs anyone in on a partner's own hostname, and no CSRF trusted origin or TLS question is touched. D-035 stays open exactly as recorded.

## Consequences

- Every product on this platform is data: four catalog rows, four `draft` integrations, no product-specific code anywhere (checked directly by a Phase 11 test that greps the four codes across `platform/`, `commercial/`, `interfaces/` and `integration/`).
- A trial and a subscription can now disagree in the good way: a customer may hold two products actively and a third on trial, which was previously unrepresentable.
- The reseller and affiliate channels needed no new code for the four products - `PartnerProductGrant`, partner price books and `CommissionRule` are already keyed by product code alone.
- Retail price / margin visibility to a partner remains **not supported** (Phase 7's decision, ADR-027/029: the partner price is the one billed price, and the partner earns commission on it, never a markup) - reported as a gap against the brief, not built as a shortcut.
