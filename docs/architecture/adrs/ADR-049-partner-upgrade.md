# ADR-049: Partner upgrade - Affiliate to Reseller or White-label on the same login

Status: accepted, 2026-10-24. Builds on ADR-028 (capabilities, not types), ADR-047 (experiences are labels over grants; `default_experience` is a landing preference) and ADR-048 (one profile-completion rule). Changes none of them.

## Context

A partner is created by Super Admin as an Affiliate (name, administrator email, password, type). Later it grows: it wants to resell, or to sell under its own brand. The owner's rule is that it must do so **on the same sign-in, the same `PartnerAccount` and the same membership** - no second user, no second account, no password reset - and that what it earned as an affiliate (referral links, attribution, conversions, commission, payouts, audit) is not lost. The portal must then open the right dashboard and menu for what the partner is *now*, while authorization stays with the capability grants.

Most of the machinery existed. `experience.transition_experience` already grants a bundle through `grant_capability`, optionally gives products, and sets the landing, all audited and atomic. What was missing was the **request workflow**: a way for the partner to ask, for staff to review, and for the server to refuse an approval that is not ready.

## Decisions

1. **One new table, no new kind of partner.** `PartnerUpgradeRequest` (`partners_upgrade_request`) is a workflow record: `partner` (the one account), `from_experience`, `to_experience` (`reseller` | `white_label`, a CHECK), `status`, a `proposal` JSON in a closed key set, `requested_by`/`requested_at`, `submitted_at`, `decided_by`/`decided_at`, staff's notes, what approving added and removed, a commercial *reference*, the request's correlation id and a version. It holds no capability, price or permission. The brief allows exactly this model "only if the existing architecture cannot model the workflow cleanly"; a request with a lifecycle, two actors and a review cannot live in `default_experience` or a grant. The migration is one `CreateModel` (a test pins that).
2. **Primary workspace is `default_experience`.** The brief's `primary_partner_workspace` is the existing column and `resolve_landing`: the stored preference intersected with what the grants open. No second column. Landing, sidebar and dashboard follow it; **it still authorizes nothing** (the existing architecture tests keep `default_experience` out of every decider, and the new modules do not read it - they ask `selectors.landing_workspace`).
3. **Lifecycle.** `requested` (started) -> `pending_approval` (submitted) -> `approved` | `rejected`; `profile_required` when staff ask for more (the partner edits and submits again); `cancelled` when the partner withdraws. A partial unique index allows **at most one open request per partner**, so two clicks or two administrators cannot raise two; asking again for the same target returns the open one, asking for another while one is open is a 409.
4. **Paths.** Affiliate -> Reseller, Affiliate -> White-label (directly: no policy requires Reseller first) and Reseller -> White-label. A pure rule over the grants and the landing (`upgrades.eligible_targets`), served to the screens; a target the partner already wears is never offered. White-label has nothing above it.
5. **Upgrading is additive: the affiliate grants are kept.** Approval grants the target bundle, makes it the landing and retires nothing. This is not only about "preserve history": `referrals.capture_referral` refuses a code whose owner no longer holds `referral.create`, so retiring the affiliate set would silently kill every referral link the partner has already published and stop it earning from them. The partner therefore ends with, for Affiliate -> Reseller, the Reseller workspace as its landing and the Affiliate workspace one click away in the workspace switcher; the "Referrals" entry of the Reseller menu is that history. The Experience panel still lets staff retire the affiliate set deliberately.
6. **Authorization of each step.**
   - Partner side (`/api/v1/partner/<id>/upgrade...`): `partner_view` (the id is verified against the caller's own active membership; another partner's id or request is a 404), then `platform.partner_profile.manage` - held by owner/admin roles only - and an *active* partner. Every member may *read* where the partner stands. These commands only ever write the request row.
   - Staff side (`/api/v1/admin/partners/<id>/upgrades...`): `staff_view` and `platform.staff_partner.manage` for any decision; `platform.staff_partner.view` to read. Nothing a partner sends reaches a decision route; there is no partner route named approve, grant or decision (a test reads the source).
7. **Approval is all-or-nothing and server-ruled** (`controlplane/partner_upgrades.approve`, one transaction): lock the partner then the request; require the request to be `pending_approval` and the partner `active`; grant through the one `transition_experience` call; for White-label apply the proposed brand and domain through the existing `update_brand` and `request_domain` commands (a domain is a *request*; nothing is served until DNS proves it, same as the partner's own portal); then require the **profile-completion rule of ADR-048** to pass for everything the partner now holds - products, commission rule, brand, referral code, business information - and roll the whole transaction back with the list of what is missing if it does not; finally stamp the request. A browser click alone can therefore never grant a commercial capability.
8. **What the partner supplies, and where it lives.** Business details (name, legal name, phone, country, tax number, billing contact) are saved to the partner's own profile with the existing `update_own_profile` - not copied into the request - and submitting checks the profile itself. The request carries only what has no home: products asked for, a pricing preference and notes, commercial notes, and for White-label the brand (name, two colours, support email) and a domain. Reseller steps: Business, Products, Pricing, Commercial, Review. White-label: Business, Brand, Products, Pricing, Domain, Review. Each step is saved as completed with the request's version, so two tabs cannot overwrite each other.
9. **Audit.** `partner.upgrade_requested`, `_submitted`, `_info_requested`, `_rejected`, `_cancelled` and `_approved`, each naming the partner, from and to. The approval entry also carries who requested and when, what was added and removed, the products given, the commercial reference and the request's correlation id; the request row keeps the same facts for the console. Entries name *sections*, never what the partner typed, and no secret is involved (an upgrade never reads or writes a password - a test greps the modules for the word).
10. **No money.** The brief asks that any set-up or onboarding fee come from Super Admin configuration and the billing architecture. **The platform has no partner set-up fee, plan or checkout**, and `NOT_IMPLEMENTED` already records that a partner pays nothing for its programme. This ADR therefore stores a staff-entered *commercial reference* (a contract or invoice number) and nothing else: no amount, no currency, no payment status, no hard-coded figure (a test searches the modules for them). A paid upgrade is a product decision for the owner (see Not built).
11. **Surfaces.** Partner: a "Grow Your Partnership" section on the Affiliate and Reseller dashboards (cards from the server's `eligible` list; an open request replaces them; White-label draws none) and a step wizard at `<workspace>/upgrade[/reseller|/white-label]`, served as pages of the dashboard entry so no new menu item appears. Staff: an Upgrade panel on the partner's detail (level, status, requested upgrade, checklist, proposal, history, Approve / Reject / Request more information), a badge on the All Partners row and a count on the Partners dashboard (`upgrades_pending`, beside - not inside - the pinned card list).
12. **Login routing is unchanged.** Authenticate -> resolve the active membership -> resolve the partner -> check its status -> load the live grants -> `resolve_landing` -> open `/partner/<workspace>/dashboard` (`/reseller/dashboard` etc. are the existing 308 redirects). Nothing in the browser (the address, local storage, a stored "partner type") is read to decide any of it.

## Alternatives

- **Retire the affiliate set on upgrade** (a "clean" Reseller menu). Rejected: it kills published referral links (decision 5). The landing and the workspace switcher already deliver the clean menu.
- **A `partner_level` column** or an enum on `PartnerAccount`. Rejected: it is `default_experience` plus the grants again, and would drift from them (ADR-047).
- **Let the partner's request carry the capability list.** Rejected: capabilities come from the registry's bundles, chosen by the server from the target.
- **Store the business details in the request and apply them on approval.** Rejected: two sources of truth for the profile, and a rejected request would leave edits unapplied that the partner can already make from Account.
- **Auto-approve when the profile is complete.** Rejected: the brief says not to fake approval the platform does not support; commercial terms are a staff decision.

## Not built (stated, not hidden)

- **A paid upgrade** (set-up fee, subscription or onboarding fee, checkout, payment success -> workflow): there is no partner billing model to attach it to. Needs an owner decision on what a partner pays and an invoice/checkout path.
- **Domain verification as a gate to activation.** A custom domain is optional in ADR-048 and cannot be *proven* before the partner holds `domain.manage`, so approval records the request and the White-label workspace's Custom Domain page carries the DNS proof afterwards.
- **Logo and favicon in the wizard.** Uploading a logo needs the White-label grant; it is done in Brand Settings after approval. The brand has no favicon.
- **Pricing and margin configuration by the partner.** Prices and commission are staff-set (the rule engine is product-level; there is no wholesale cost). The wizard records a preference and notes for the reviewer.
- **A cross-partner review queue screen.** The API exists (`GET admin/partner-upgrades`); staff reach requests through the badge and the partner's page.

## Consequences

- One additive table; the previous release neither reads nor writes it, so the migration is overlap-safe.
- Upgraded partners hold the union of their grants; the Experience panel, the workspace switcher and reports already handle that case.
- A later change that lets a partner pay for an upgrade attaches to `approve` (a precondition) without touching the request model.
